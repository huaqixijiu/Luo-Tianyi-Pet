# 决策记录

本文件追加重要决策。新决定可以取代旧决定，但要注明替代关系，不能删除历史原因。

## ADR-001：使用 C#、.NET 10 LTS 和 WPF

- 日期：2026-08-30
- 状态：已采用
- 决定：主程序采用 C#、.NET 10 LTS 和 WPF。
- 原因：项目只面向 Windows，并大量依赖透明窗口、Win32、Core Audio、OLE、COM 和 Shell 能力；WPF 的窗口互操作成熟，适合先完成个人桌宠。
- 影响：不追求跨平台；现代 Windows API 通过平台适配层接入。

## ADR-002：把仓库作为跨对话记忆

- 日期：2026-08-30
- 状态：已采用
- 决定：`AGENTS.md` 规定每轮恢复流程，`docs/项目总控.md` 保存当前状态，开发日志保存验证历史。
- 原因：聊天可能变长、压缩或切换任务，不能依赖模型对旧对话的隐式记忆。
- 影响：每个可交付变更必须同步更新项目总控和开发日志，否则不算完成。

## ADR-003：原始素材和运行时素材分离

- 日期：2026-08-30
- 状态：已采用
- 决定：`候选素材_官方/` 只保存原始来源；`assets/` 保存可追溯的运行时派生资产。
- 原因：现有格式和画布差异较大，直接在 UI 中混用解码器会增加故障和性能风险。
- 影响：建立资产编译工具、动画清单、来源哈希和转换参数。

## ADR-004：显示模式、持续状态和一次性反应分离

- 日期：2026-08-30
- 状态：已采用
- 决定：不使用一个枚举表示桌宠全部状态；调度器从三个正交状态生成播放计划。
- 原因：QQ提醒、音乐、睡眠和用户选择模式会交叉；单一状态容易在动画结束时恢复错误。
- 影响：所有平台联动只能发领域事件，不能直接命令窗口播放并写死返回动画。

## ADR-005：安全降级优先于功能命中率

- 日期：2026-08-30
- 状态：已采用
- 决定：受保护应用前台、通知权限拒绝、回收站不可用或媒体结果不确定时，功能可以不触发，但不能绕过权限或给出错误成功反馈。
- 原因：账号安全、文件安全和隐私高于动画完整性。
- 影响：每个外部联动必须提供禁用、超时、取消和恢复路径。

## ADR-006：音乐状态临时覆盖显示，不修改用户模式选择

- 日期：2026-08-30
- 状态：已采用
- 决定：音乐开始后播放“享受音乐”并进入“音乐摇摆”；音乐停止后恢复用户此前选择的迷你或完整全身模式。
- 原因：保留已经确认的音乐专属待机，同时不让音乐事件永久改变用户的交互选择。
- 影响：设置中需要分别保存 selected display mode 和 resolved playback state。

## ADR-007：运行时统一使用透明 PNG 图集和帧时序清单

- 日期：2026-08-30
- 状态：已采用
- 决定：选定的 GIF、动态 WebP 和 PNG 在构建前编译为透明 PNG 图集；WPF 根据带来源哈希的 JSON 清单逐帧裁切播放。
- 原因：WPF 对现有动画格式的原生支持不一致；统一图集可以准确保留透明度、毫秒级帧时长、循环次数和结束回调，并减少运行时解码器依赖。
- 影响：新增可复现的图集生成脚本和清单校验器；原始文件继续保留，图集通过 Git LFS 管理；需要在 M1 完成内存稳定性验证。

## ADR-008：每次播放会话随机选择一个音乐持续动画

- 日期：2026-08-30
- 状态：已采用；覆盖 ADR-006 中“享受音乐后固定进入音乐摇摆”的两阶段描述，ADR-006 的显示模式恢复约束继续有效。
- 决定：每次从暂停或停止进入播放状态时，在 0.5 倍速“享受音乐”和“音乐摇摆”中随机选择一项，并让它在整个播放会话中循环；暂停后继续播放重新选择。
- 原因：两种素材人物大小、服装和画风不同，播放中途强制切换仍会让体验割裂；按播放会话选择可保留随机性并避免会话内换装。
- 影响：两项素材都必须支持无限循环；持续状态保存当前会话选中的动画，音乐停止后仍恢复用户原本选择的“嘿嘿”或完整全身模式。

## ADR-009：使用只读 Core Audio 会话峰值判断网易云是否有声

- 日期：2026-08-30
- 状态：已采用
- 决定：通过 Windows Core Audio 枚举默认多媒体输出设备的会话，以公开的会话进程号匹配 `cloudmusic.exe`，读取归一化峰值；使用 `NAudio.Wasapi` 3.0.1 作为薄封装。默认每 250 毫秒读取一次，峰值达到 0.001 立即视为播放，连续 1.5 秒无声才视为停止。
- 原因：用户要求不接网易云私有接口；单纯检查进程无法区分播放和暂停，而公开音频会话峰值无需注入、Hook、内存读取或网络监听。
- 影响：功能可以在运行时配置中单独关闭；会话消失立即停止，临时探测失败保留上次状态并重试；不记录进程号、峰值或歌曲信息。真实播放器在不同输出设备、静音歌曲和独占输出下仍需端到端验证。

## ADR-010：将音乐静音宽限缩短为 0.5 秒

- 日期：2026-08-30
- 状态：已采用；覆盖 ADR-009 的 1.5 秒默认宽限参数，其余检测方案不变。
- 决定：连续检测到 0.5 秒无声后退出音乐状态并恢复用户选择的“嘿嘿”或完整全身模式。
- 原因：1.5 秒会让暂停操作显得迟钝；0.5 秒仍能过滤极短的采样空隙，同时明显改善暂停反馈速度。
- 影响：用户 `settings.json` 配置版本升级为 2；旧版本恰好使用原默认值 1500 毫秒时自动迁移为 500 毫秒，用户已设置的其他数值保持不变。

## ADR-011：将音乐静音宽限调整为 1.0 秒折中值

- 日期：2026-08-30
- 状态：已采用；覆盖 ADR-010 的 0.5 秒默认宽限参数。
- 决定：连续检测到 1.0 秒无声后退出音乐状态；未来由桌宠发起的上一首/下一首操作使用独立加载状态，不再只依赖静音宽限判断。
- 原因：0.5 秒会把网易云切换下一首时的常见加载时间误判为暂停，1.5 秒又让真实暂停反馈偏慢；1.0 秒作为当前只读检测阶段的折中值。
- 影响：用户 `settings.json` 配置版本升级为 3；版本 1 的旧默认 1500 毫秒和版本 2 的旧默认 500 毫秒均迁移为 1000 毫秒，其他自定义值保持不变。

## ADR-012：全局快捷键发送采用失败关闭的用户级输入适配器

- 日期：2026-08-30
- 状态：已采用。
- 决定：网易云控制只使用普通用户权限的 `SendInput` 发送用户配置组合；发送前确认前台进程不在受保护名单，并检查相关实体键未被用户按住。前台查询不可靠、输入被占用、过于频繁或系统未完整接受时一律不发送或报告失败。
- 原因：桌宠需要复用网易云自身全局快捷键，同时不得把组合键送入原神等受保护应用，也不能打乱用户正在进行的键盘输入。
- 影响：默认提供 `Ctrl+Alt+Left`、`Ctrl+Alt+P`、`Ctrl+Alt+Right` 作为首轮可见配置；右键菜单显示当前组合。快捷键“已发送”与播放器“已响应”是两个事件，只有后者可触发 OK，下一阶段需用音频状态变化完成确认、加载和超时闭环。

## ADR-013：媒体控制改为角色内悬浮控制条

- 日期：2026-08-30
- 状态：已采用；覆盖 ADR-012 中“右键菜单显示媒体组合”的临时界面决定，ADR-012 的输入安全约束继续有效。
- 决定：鼠标移入角色后显示上一首、播放/暂停、下一首、喜欢歌曲四键控制条，移出后隐藏；控制条覆盖在现有透明窗口底部，不扩大桌宠常驻窗口。喜欢歌曲使用网易云默认 `Ctrl+Alt+L`。
- 原因：常用媒体操作需要比右键子菜单更直接，并与用户给出的简洁播放器按键参考保持一致；悬停显示可避免长期占据屏幕和遮挡角色。
- 影响：右键菜单只保留显示模式、调试、置顶和退出等低频功能；按钮工具提示显示当前快捷键，播放/暂停字形跟随检测状态，控制条隐藏时不得参与身体命中。

## ADR-014：悬浮媒体组件使用项目内轻量矢量样式

- 日期：2026-08-30
- 状态：已采用；细化 ADR-013 的视觉与显隐行为。
- 决定：媒体控制岛使用洛天依代表色 `#66CCFF`、蓝色玻璃表面、本地 WPF `Path` 矢量图标和轻量淡入淡出控制器；只在指针停留于桌宠窗口时可交互，移出后经过 220 毫秒宽限隐藏。
- 原因：MahApps、MaterialDesignInXaml 和 WPF-UI 都提供成熟按钮与图标组件，但当前只需要四个按钮；引入整套框架会增加包体、主题资源和升级风险，本地组件可以保留同样的圆形按钮、状态反馈和 DPI 清晰度。
- 影响：当前不新增第三方 UI 依赖；后续设置页若需要大量标准控件再单独评估 UI 框架，媒体组件仍可复用当前品牌色和矢量图标资源。

## ADR-015：媒体控制岛移到角色动画正下方

- 日期：2026-08-30
- 状态：已采用；覆盖 ADR-013 中“覆盖在现有透明窗口底部、不扩大窗口”的布局决定，四键内容和显隐规则不变。
- 决定：为媒体控制区在窗口底部预留 58 DIP，高度随当前动画画布一起计算；角色视觉层与音乐切换闪白层均避开该区域。控制岛只在悬停期间显示，但即使显示也不覆盖角色、表情文字或身体命中区。
- 原因：用户希望控制按钮出现在动画正下方，不能挡住桌宠本身；单纯继续缩小覆盖层会损害按钮可点性和视觉层级。
- 影响：窗口高度比素材显示高度多 74 DIP（基础边距 16 DIP 加控制区 58 DIP），桌宠主体尺寸不变；旧窗口位置仍可恢复，贴近屏幕下缘时由现有工作区约束校正。

## ADR-016：新增官方动态素材先进入独立候选区

- 日期：2026-08-30
- 状态：已采用。
- 决定：将洛天依 12 周年 QQ 动态表情的 16 个 300×300 原始 GIF 放入独立“新添加”目录，在动画挑选器中统一显示蓝色标记并提供专用筛选；不自动写入运行时状态映射。
- 原因：这组素材覆盖场景广，但画风、动作时长和语义仍需用户实际预览后决定，直接接入会推翻已确认的动画规则。
- 影响：素材来源、归档提交、原始文件名和 SHA-256 都随目录保存；用户选择前，程序包大小和运行时行为不受这些候选影响。

## ADR-017：曲目信息使用系统媒体会话并以网易云窗口标题兜底

- 日期：2026-08-30
- 状态：已采用。
- 决定：曲名和歌手优先读取 Windows `GlobalSystemMediaTransportControlsSessionManager`；目标网易云没有注册系统媒体会话时，只读其顶层主窗口标题并按“歌曲 - 歌手”解析。角色上方预留 52 DIP 显示曲名，悬停时显示，曲目变化或切歌后保留 4 秒。
- 原因：系统媒体会话是语义最可靠的公开来源，但用户当前运行的网易云实测没有任何系统媒体会话；窗口标题仍由 Windows 桌面管理器公开，能够在不接入网易云接口、不读取进程内存的前提下满足功能。
- 影响：只匹配 `cloudmusic.exe`，不枚举其它应用内容；标题和歌手只在内存中保存，日志只记录“曲目已变化”事件而不记录文本。网易云标题为空、通用或格式改变时显示安全降级文案。

## ADR-018：启动按本地时间问候，系统恢复统一播放苏醒

- 日期：2026-08-30
- 状态：已采用。
- 决定：桌宠启动时按 06:00～12:00、12:00～13:30、13:30～20:00、20:00～次日 06:00 四个半开区间播放一次既定问候；Windows 解锁或电源恢复统一播放“心律共鸣·苏醒弹出”，5 秒内的解锁/电源重复事件只响应一次。
- 原因：启动问候表达当前时间，而同一轮系统唤醒常会同时触发两个 Windows 事件；统一苏醒语义并去重可避免恢复时连续换装和重复打扰。
- 影响：时间边界由 Core 解析器和自动化测试维护；平台层只订阅公开 `SystemEvents`，不安装服务或 Hook。反应不激活、不置顶，结束后恢复用户选择的显示模式和当前音乐等持续状态。

## ADR-019：长待机睡眠复用输入空闲查询并与系统苏醒去重

- 日期：2026-08-30
- 状态：已采用。
- 决定：每秒使用既有公开 `GetLastInputInfo` 读取系统空闲时长；5 分钟进入“躺平”，15 分钟且无音乐时进入“晚安浮动”。睡眠后的首次输入播放一次“心律共鸣·苏醒弹出”，并与 Windows 解锁/电源恢复共用 5 秒去重门。
- 原因：轮询公开的累计空闲时长足以判断状态，不需要键盘/鼠标全局 Hook；真实睡眠恢复通常同时产生输入、会话和电源事件，共用去重可以避免同一动作被播放两次。
- 影响：桌宠不记录具体按键、鼠标位置或输入内容；音乐、拖拽和安全隐藏状态不会被空闲规则覆盖。睡眠素材为官方静态 PNG 的可追溯单帧图集，低幅度漂浮由 WPF 在运行时生成。

## ADR-020：原神存在性使用低频过滤进程枚举

- 日期：2026-08-30
- 状态：已采用。
- 决定：正式应用每 2 秒只按配置的 `YuanShen` 与 `GenshinImpact` 名称执行一次普通权限进程枚举，只读取进程标识并立即释放对象；启动时存在的进程仅作为基线，不补播启动反应。前台和全屏状态另用公开 Win32 窗口 API 失败关闭。
- 原因：原计划采用的 WMI `Win32_ProcessStartTrace` / `StopTrace` 在本机普通用户会返回“拒绝访问”；要求提权会扩大风险，轮询公开进程表即可满足低频桌宠场景，并更容易审计其读取边界。
- 影响：检测延迟上限约为 2 秒，不新增 `System.Management` 依赖；不读取游戏内存、模块、线程、文件、画面或网络，不向游戏发送输入，也不建立长期游戏句柄。若一次枚举失败，保留上次状态并在下一轮重试，不猜测启动或退出。

## ADR-021：消息提醒使用有包身份的 Windows 通知监听器

- 日期：2026-08-30
- 状态：已采用；真实授权等待 MSIX 测试包。
- 决定：QQ/微信提醒只使用 `UserNotificationListener` 的应用来源元数据。应用必须先具备 MSIX 包身份并声明 `uap3:userNotificationListener`；设置页仅在用户明确点击后从 UI 线程申请权限。当前免安装 EXE 检测到没有包身份时显示原因并安全停用，不尝试绕过。
- 原因：通知监听器能在不接触聊天进程内部数据的前提下提供可靠的来源分类，但 Windows 将该能力绑定到包身份和用户同意。任务栏闪烁只能作为以后另行验证的兼容性补充，不能冒充已收到消息。
- 影响：平台层只读取 AUMID、应用显示名和创建时间，从不访问消息负载；Core 只在内存中保留来源和时间做 3 秒去重。实际 QQ/微信通知测试需要先构建、签名并由用户安装 MSIX，再由用户亲自批准通知访问。

## ADR-022：测试 MSIX 使用自包含发布和未自动信任的开发证书

- 日期：2026-08-30
- 状态：已采用；等待用户确认安装。
- 决定：用微软 `WinAppCLI` 将 .NET 10 `win-x64` 自包含输出打为 MSIX；包名、发布者和版本由仓库清单固定。首次构建生成随机密码自签名开发证书，PFX 与密码只留在 Git 忽略的本地 `artifacts/msix/private/`，发布目录只放 MSIX、公钥 CER 和 SHA-256。
- 原因：自包含包不依赖目标机预装 .NET；确定性脚本比手工打包更容易审计通知能力和包内容。开发证书可以用于本机旁加载，但自动信任证书会改变系统安全状态，不应由普通构建步骤代替用户决定。
- 影响：当前包约 103 MB，签名完整但在信任公钥前会显示证书链不受信任。构建脚本不会安装证书、应用或申请通知权限；这三项依次等待用户明确确认。正式分发仍需要受信任的生产证书或 Microsoft Store 签名。
